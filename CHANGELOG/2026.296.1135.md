# 2026.296.1135 — feat(kubevirt): four CI-pool tiers, each labelled with the size it actually is

## Summary

**Supersedes `opencharly/distro-ubuntu#55`**, auto-closed at five counting verdicts; a fresh branch and thread, same content.

A kubevirt deploy may not set `cpu`/`memory` on a `from:` template — the schema is a closed disjunction (`from:` XOR an explicit spec), measured as `from: field not allowed`. So a fleet's size must be a template. One size cannot serve both repos either: `openclaw-enterprise` routes its 8/16/32-vcpu lanes to those blacksmith labels **by name**, so a runner must genuinely be that size or the label lies.

Four tiers, beside the untouched base:

| Template | Size | Serves |
|---|---|---|
| `githubrunner-ubuntu-vmi-2vcpu` | 2 vCPU / 4 GB | docs, scripts, go-install, aggregators; enterprise 2-vcpu lanes |
| `githubrunner-ubuntu-vmi-8vcpu` | 8 vCPU / 20 GB | crabbox's Go test/coverage shards (2 runners, 4 vCPU each) |
| `githubrunner-ubuntu-vmi-16vcpu` | 16 vCPU / 32 GB | Go modules, the coverage matrix; enterprise 16-vcpu lanes |
| `githubrunner-ubuntu-vmi-32vcpu` | 32 vCPU / 60 GB | the largest slice; enterprise 32-vcpu lanes |

## Why this shape, and not bigger everywhere

A CI fleet's throughput is **slots × cores**, capped by the cluster's **96 physical cores**. 27 slots across ~130 guest cores is already a 1.35× overcommit, so enlarging every runner cannot create more compute — it only moves cores between jobs. The tiers therefore put the most cores behind the lanes that dominate wall time (`Go modules` 23 min, the coverage/shard matrix 7–14 min) and give the light jobs a small host of their own, one runner per VM, so a docs run never shares a host with a Go build.

## On the duplication (stated plainly)

The four templates are **full copies** of the base spec, differing only in `cpu.cores` and `memory`. A kubevirt template can neither inherit from another template nor be overridden by a deploy (`from:` XOR an explicit spec), so repeating the body is the only way to express a size. The alternative — one template and per-deploy overrides — is exactly what the schema rejects with `from: field not allowed`.
