# 2026.296.0051 — fix(github-runner): do not relocate the Go build cache

## Summary

Stop relocating the Go **build** cache to a custom persistent path. `GOMODCACHE`/`GOPATH` remain
shared per VM (module content is immutable; the download is the expensive part). `GOCACHE` is left
at Go's DEFAULT: a per-USER cache (`~/.cache/go-build`) that the VM's runners already share — the
removal targets the custom path and its root-side ownership, not sharing as such. A negative check
(`! grep -q '^GOCACHE=' .env`) makes a re-introduction fail the build.

## Root cause (R1)

A CI coverage job failed while linking a generated fixture:

```
--- FAIL: TestGenerateEnvironmentSplit (0.41s)
    main_test.go:1135: generated scalar fixture: exit status 1
        # command-line-arguments.test
        panic: could not look up runtime.mapinitnoop
        cmd/link/internal/ld.(*deadcodePass).init(...)
        FAIL command-line-arguments [build failed]
FAIL github.com/openclaw/crabbox/scripts/configgen
```

The failure appeared only after the recipe pointed `GOCACHE` at a shared, persistent
`/var/cache/charly/go/build`. The custom path was created root-side and its ownership then had to be corrected so the runner
user could write it; `actions/setup-go`'s post step subsequently failed `EACCES` on the parent.
Reverting to Go's default removes both the custom path and that ownership surgery. The exact
trigger of the linker panic is not fully proven — the honest statement is that the custom,
root-created build-cache path is what changed, so it is what is removed.

**Missed control:** the change shipped as a performance optimisation without a bed assertion for
"a generated fixture links", and the only evidence was wall-clock improvement. This PR keeps the
safe half and drops the unsafe half.
