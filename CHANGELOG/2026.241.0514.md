# 2026.241.0514 — fix: advance the charly candy refs off pre-cutover tags

## Summary

Three candy refs still pointed at **pre-cutover charly tags**. Those tags' trees carry
`candy/plugin-mcp`, `candy/plugin-record`, `candy/plugin-cdp`, `candy/plugin-dbus`,
`candy/plugin-wl`, `candy/plugin-vnc` and the `plugin-example-*` candies **inline** — they were
de-submoduled into standalone repos afterwards. A consumer that composes this repo alongside those
standalone repos therefore sees the same candy name provided by two repos and reports a
`remote candy name conflict`.

Both candies still exist at the current charly tag, so this is a pure tag advance to
`v2026.241.0413` — no repointing needed.

## Why it was invisible here

This repo validates clean **either way** — in isolation the old refs resolve perfectly well:

```
$ charly box validate      # before
exit=0, 0 errors
$ charly box validate      # after
exit=0, 0 errors
```

The cost lands on consumers. `charly` composes this repo as a `box/*` submodule, and fetching a
charly candy ref also materialises that charly tag's **own** nested `box/*` submodules — so a
stale ref here propagates into every project that reaches this repo transitively.

## Scope — stated plainly

**This change alone does not clear charly's conflicts.** Measured, with charly's `box/*` pointed
at this branch:

```
$ charly box validate      # in the charly project
exit=1, 18 errors  (16 remote-candy-name conflicts + 2 unrelated check-keepalive)
```

`distro-ubuntu` and `distro-debian` carry the identical defect and both must advance; each has its
own PR. Beyond those, charly's own `box/*` gitlinks are behind and need a sync PR, and only a
charly tag cut *after* all of that has clean nested boxes. This PR removes one source and is
correct on its own terms; it is not sold as the whole fix.

I verified this rather than assuming it: I first expected this repo alone to clear the conflicts,
measured that it did not, and traced the remainder to the sibling repo and the recursive
`box/*` fan-out before writing this.

## How tested

`charly box validate` in this repo, before and after, on the final committed tree with a clean
worktree — exit 0 and zero errors in both states, which is the honest result: the change is
consumer-visible only.

The target tag was checked to actually contain what the refs need, rather than assumed from its
date:

```
$ git -C <charly> ls-tree v2026.241.0413 candy/ | grep -E 'candy/(charly|charly-mcp)$'
candy/charly-mcp
candy/charly
$ git -C <charly> ls-tree v2026.241.0413 candy/ | grep -c 'candy/plugin-'
0
```

Both candies present; **zero** inline `plugin-*` candies, which is precisely the property the old
tags lacked.
