## Summary

The proven Ubuntu 24.04 GitHub Actions runner VM was a single 348-line box whose entire content was the
runner install — cloud-init, registration, service wiring — all of it box-local deploy steps. Nothing could
compose it, and nothing could test it without standing up the whole box. That is the wrong shape for
something that is a *capability*, not a *venue*.

It is now an entity, three pieces:

| piece | what it is |
|---|---|
| `candy/github-runner-ubuntu/` | 303-line candy, 42 plan steps (13 file steps, 26 deploy commands, 3 checks), with its 13 recipe files mirroring their absolute paths under `files/` |
| `githubrunner-ubuntu` | the box cut to a 25-line substrate: base + timezone, nothing else |
| `githubrunner-ubuntu-vmi` | `kind: kubevirt` TEMPLATE — `cluster: quant-dev`, `namespace: default`, `distro: ubuntu`, `ssh_user: ubuntu`, `cpu: {cores: 16}`, `memory: 32G`, `machine: q35`, EFI firmware, `run_strategy: Always`, and `source: {kind: container_disk, image: ttl.sh/charly-githubrunner-ubuntu-disk:6h, disk_path_in_image: /disk/disk.img}` |
| `githubrunner-ubuntu-disk` | the boot-disk builder: a `vm:` entity over the noble cloud image at `disk_size: 128G`, with the `ssh:` block and `qemu-guest-agent` the KubeVirt guest needs. `charly vm build <this> --container-disk --push` produces the OCI disk the template boots |
| `check-githubrunner-ubuntu-disk` | the boot-disk builder's OWN bed: a `vm:` deploy of that entity, so the substrate BUILDS what it boots (`[vm-build] PASS 33.986s`) and a defect in the builder fails this gate. `ok: True`, 183s, 0/0/0 |
| `quant-dev` | the external cluster profile: `kubeconfig_context: kubernetes-admin@quant-dev`, `default_namespace: default`, `admission_policy: privileged`, `storage.class_default: csi-cinder-high-speed-gen2` |
| `check-githubrunner-ubuntu-vm` | the disposable bed: this candy added to the substrate, `disposable: true`, `lifecycle: dev`, 12 plan steps |

The whole thing is declared in `charly.yml` and driven by nothing but the `charly` binary, which is the
constraint the extraction had to satisfy.

**Reproducibility, separated by leg rather than asserted as one claim.** There are three beds and they do
not have the same dependency:

| bed | produces what it tests? |
|---|---|
| `check-githubrunner-ubuntu-vm` (libvirt) | **yes** — the substrate builds the box it boots, `[vm-build]` |
| `check-githubrunner-ubuntu-disk` | **yes** — same mechanism, which is what gives the disk builder the coverage it needs |
| `check-githubrunner-ubuntu-vmi` (kubevirt) | **no** — it boots a `container_disk` by image reference |

A kubevirt deploy can only reference a *same-kind* template (`deploy.cue`: `from:` is the same-kind
template ref) and its source vocabulary takes an **image ref**, not a build. So the KubeVirt leg consumes
`ttl.sh/charly-githubrunner-ubuntu-disk:6h`, produced by
`charly vm build githubrunner-ubuntu-disk --container-disk --push <ref>` — the command is in the entity's
own comment. `ttl.sh` expires it by design, so **that one leg's green is not reproducible from the
committed tree alone**; the other two are.

This is a limit of the KubeVirt substrate's expressive surface, not a deferral: there is no step intent or
context that produces the artifact (`#Context` is `build | deploy | runtime`, and a `build`-context step
validates but contributes no step to a deploy plan — measured). Making the KubeVirt source arm able to
reference a disk entity is filed as opencharly/plugin-kubevirt#36.

## Filed issues

- `opencharly/plugin-kubevirt#36` — a kubevirt source cannot be built: no link from a kubevirt deploy to a
  disk-producing entity. This is why the KubeVirt leg consumes a pushed artifact rather than producing it.
- `opencharly/plugin-kubevirt#35` — a kubevirt deploy cannot name its own venue (both `cluster:` and
  `kube_context:` make the loader classify the node as a template and reject `add_candy`/`disposable`), yet
  `charly update` resolves the venue from the deploy. The workaround here was to set a current-context on the host.
- `opencharly/layer-cuda#7` — the `cuda` candy pinned `cuda-cccl-devel`, which no repo it enables provides
  (the repo these packages actually resolve from names it `cccl-devel`), so every GPU image failed its dnf
  transaction.
- `opencharly/layer-nvidia#9` — the driver-lib check demanded `exit_status: 0` from an `ls` that exits 2
  whenever any candidate is absent, so it had never passed on any image; plus an Arch-only candidate list
  that never intersected the Fedora VA-API driver.

The first two are capability gaps in the KubeVirt substrate that this change had to route around; the last
two gated `check-ollama-pod` in distro-fedora, which is what let the released plugin charly then needed
build. None is a workaround of *this* change.
