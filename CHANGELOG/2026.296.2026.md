# 2026.296.2026 — feat(ci): give the blacksmith runner tiers nested virtualisation (host-passthrough CPU)

## Summary

Give the four blacksmith-labelled Ubuntu CI runner tiers **real KVM and nested
virtualisation**, and prove it inside one guest — the consumer leg of the work
tracked in `opencharly/opencharly#607`.

**The mechanism (measured, and it is not host-device passthrough).** KubeVirt's
default `cpu.model: host-model` exposed neither `svm` nor `/dev/kvm` to the
guest. A `host-passthrough` CPU does: the guest's **own kernel** then loads
`kvm_amd` (or `kvm_intel`) and creates `/dev/kvm`. So:

- `charly.yml` — the four tiers `githubrunner-ubuntu-vmi-{2,8,16,32}vcpu` each
  get `cpu: {cores: N, model: host-passthrough}`. The four are full standalone
  copies because a kubevirt `from:` is a closed disjunction; each keeps its own
  tier comments.
- `candy/github-runner-ubuntu/charly.yml` — the recipe adds the runner user to
  the `kvm` group (`/dev/kvm` is `0660 root:kvm`, so a job run directly as the
  runner user could not open it) and a runtime `check:` asserts the user really
  can open the device.

**`devices.host_devices` is deliberately NOT used, because it cannot work here.**
Measured on this cluster:

```console
$ kubectl --context kubernetes-admin@quant-dev create --dry-run=server -f -   # a VMI with devices.hostDevices
The request is invalid: spec.HostDevices: Host Devices feature gate is not enabled in kubevirt-config
```

The `HostDevices` gate is Alpha and off on `quant-dev`, and KubeVirt's
host-device address pools are PCI/MDEV/USB only — a device-plugin resource
cannot pass a character device such as `/dev/kvm`. The renderer and schema
field that merged earlier (`plugin-kubevirt#43`, `spec#277`) remain valid for
real PCI passthrough; they are not the nested-virtualisation route. This is a
measured correction to the plan of record and is reported on `#607`.
