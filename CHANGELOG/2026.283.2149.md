# 2026.283.2149 — feat(ubuntu): land the CI-runner Ubuntu VM (entity + R10 bed + skill)

## Summary

Lands the **CI-runner Ubuntu VM** the org's self-hosted fleet already runs on host `no`, as a
first-class entity in this repo — next to `ubuntu-debootstrap` and its bed, the way the
CachyOS half of the fleet lives in `opencharly/distro-cachyos` beside `box/githubrunner` and
`check-githubrunner-pod`.

Why the VM exists at all: the Blacksmith-shaped CI of `opencharly/openclaw-enterprise` needs a
**rootful Docker daemon, privileged k3s node containers with `br_netfilter` on the node
kernel, systemd and apt + passwordless sudo** — none of which a rootless pod provides on any
image. Those workflows are also written for **one job per machine** (their runners are
per-job VMs); this VM runs **four** runners on one host, so the recipe is a collection of
co-tenancy fixes, one per failure measured live on 2026-10-10:

| Piece | The failure it prevents |
|---|---|
| Docker pinned to `29.4.0` and `apt-mark hold` | the CI's own `setup-test-docker` action installs *and asserts* `docker version = 29.4.0`; a drifted daemon fails that lane's assertion |
| The daemon runs as `docker-ci.service` on `/run/docker-ci.sock`; stock `docker.service`/`docker.socket` stay installed but inactive | a lane's `systemctl stop docker.service docker.socket` (logging-collector's setup) otherwise kills its co-tenants' daemon — measured: `14:07:16 Stopping docker.service` → `14:07:28` `Images and Packaging` `docker buildx create` → *Cannot connect to the Docker daemon at unix:///var/run/docker.sock* |
| `/var/run/docker.sock` kept as a symlink to that socket | lanes, helpers and tests hardcode or mount that path (`runtime-image-fixture.mjs`, `docker-compute-token-retry`, the production-compose mounts) |
| `DOCKER_HOST=unix:///run/docker-ci.sock` in every runner's `*.service.d/docker-host.conf` | a lane that relinks the shared symlink otherwise redirects its co-tenants |
| `charly-docker-sock-heal.timer` (30 s) | repairs a socket path such a lane left dangling, without fighting one that legitimately relinked it |
| `charly-docker-store-gc.timer` (10 min) | every `docker/setup-buildx-action` starts a buildkit builder container with its own anonymous cache volume, and a lane that is cancelled, times out or whose runner restarts leaves it **running**, where `docker container prune` can never reach it. Measured: **13 such builders held 84 GB and filled the guest to 100 %**, after which lanes failed with ENOSPC and their logs were no longer uploadable (`BlobNotFound`, including lanes that never touched Docker) |
| journald capped at 200 MB | a log flood cannot fill the disk either |
| unprivileged user namespaces enabled | Ubuntu 24.04 restricts them via AppArmor by default, which breaks lanes that sandbox themselves with bubblewrap — `Image Runtime Startup`: `bwrap: loopback: Failed RTM_NEWADDR: Operation not permitted` |
| 128 GiB disk / 32 GiB RAM / 16 vCPU / 8 GiB swapfile | measured: four concurrent lanes peaked at ~12 GiB on the 15 GiB original and produced 44 GiB of Docker state on the 61 GiB original |

The bed asserts, each anchored on the mechanism rather than a proxy for it:

1. `docker-version-pinned` — the daemon's server version is exactly `29.4.0`.
2. `daemon-unit-split` — `docker-ci.service` active and stock `docker.service` inactive.
3. `socket-and-per-runner-docker-host` — `/var/run/docker.sock` resolves to the daemon socket
   and all four runner drop-ins set `DOCKER_HOST` to it.
4. `cotenant-isolation-under-lane-mutation` — executes the mutation: stop the stock unit,
   relink the shared symlink, then prove a `DOCKER_HOST` co-tenant still reaches a live daemon
   and the heal restores the path.
5. `store-gc-collects-leaked-builder` — with one process really **named** `Runner.Worker`
   representing an active job and two builders present, the GC drops only the leaked one (two
   hours stale) and keeps the active job's.
6. `unprivileged-user-namespaces` — a real `uid_map` write inside a new user namespace
   succeeds.
7. `runner-tree-and-labels-ready` — the runner tree plus both exact label sets.
8. `resources-and-timers` — both timers active, journal capped, the root filesystem really is
   the 128 GiB disk, the swapfile is on.

**Every store-GC behaviour now has a step that fails without it** (the validator's second
finding). The GC's thresholds are overridable so the bed can drive each branch — the age
grace on the idle purge, and the pressure percentage — and the four behaviours are covered:
the surplus-builder rule, the stale docker-context/buildx-state repair, the idle purge, and
the while-running disk-pressure purge. Two of those branches were previously no-ops under
the fixture, and driving them found two real defects (below).

Six defects the R10 iterations caught in this change, all fixed here (kept in the record
deliberately — the gate earned its keep):

- the GC counted active jobs with `pgrep -f Runner.Worker`, which matches any process whose
  **command line** mentions the string, including the bed's own check; the inflated count made
  the surplus rule keep a leaked builder. It now counts by process **name** (`pgrep -xc`), and
  the fixture creates a process genuinely named `Runner.Worker`.
- the sizing assertion compared against a guessed string (`122G`); the filesystem reports
  `122.9G`. It now asserts the magnitude, which is what the step means.
- the GC parsed `buildx ls` for names shaped `builder-<hex>` — the shape `setup-buildx-action`
  generates — so a builder created under any other name was invisible to the surplus rule.
  It now takes buildx's whole inventory, excluding only the built-in `default` builder.
- **the idle purge never fired**: `jobs=$(pgrep -xc Runner.Worker || echo 0)` captures TWO
  lines, because `pgrep -c` prints its zero count *and* exits 1, so `[ "0\n0" -eq 0 ]` failed
  with "Illegal number" and the branch fell through to the disk-pressure operand. That is the
  branch that collects a dead lane's leftovers, and it was silently dead in production too.
- docker REJECTS a zero age (`--filter until=0m` -> "invalid filter"), so a zero threshold now
  means "no age floor" and skips the filter instead of emptying the id list.
- two fixture/timing traps, both now recorded in the bed: the checks must not assert before
  cloud-init has converged (`cloud-init status` alone reports the *previous* boot's result for a
  few seconds), and **`charly vm build` skips when a disk already exists**, so a cloud-init
  change re-run against a reused disk proves the *old* recipe. The bed's description carries the
  command to force a fresh disk, because three iterations were lost to that one.

### On `check:` vs `command:` (the validator's non-blocking note)

A `check:` step carries prose plus at most one verb-position key (the check skill's rule), so
the verbatim script copies that sat in `check:` next to an identical `command:` were redundancy
(R2) and are gone: `check:` is now one-line intent and `command:` is the single executed script.
Steps that use the sugar form (`check: command=…`) keep it, which is the shape the sibling
`check-ubuntu-debootstrap-vm` bed uses.
